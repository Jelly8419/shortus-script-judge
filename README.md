# 쇼더스 대본 품질 판정기

렌더링 전에 쇼더스 대본을 **쇼더스가 실제로 사용한 원문**과 대조해 **통과 / 보류**를 판정한다. 보류면 결함 유형·문제 섹션·근거 인용을 함께 내고, 참고용으로 품질 점수와 진단을 붙인다.

## 한눈에 보기

**좋은 대본의 기준.** 보류는 "시청자가 이 대본만 보고 틀린 사실을 믿게 되는가" 하나로 결정한다 (사실 오류, 범위 확대, 귀속 오류, 의미 왜곡, 입력 부족, 그리고 건강·금융 주제의 확실성 변화). 훅, 훅 회수, 흐름, 핵심 누락, 글의 목적 보존은 장르별 가중치를 둔 참고 점수로 낸다. 길이(30~45초)는 근거를 따져본 뒤 게이트에서 뺐다.

**검증.** 직접 판정한 실제 대본 11건(보류 7 / 통과 4)과, 통과 대본에 결함을 하나씩 심은 주입 세트 10건(결함 7 + 대조군 3)으로 확인했다. 결함 유형뿐 아니라 **사람이 짚은 섹션을 잡았는지**까지 맞아야 정답으로 셌다.

| 최종 구성 (프롬프트 v2a + 유형 재분류, gpt-4.1, 3회 반복) | 결과 |
|---|---|
| 실제 대본: 맞는 이유로 보류 | 4/7 (s01은 엉뚱한 섹션으로 보류, s03·s10 놓침) |
| 실제 대본: 오탐 | 0/4 ~ 1/4 (6회 중 2회 s07 요일 오탐) |
| 주입 결함: 맞는 이유로 보류 | 5/7 |
| 주입 대조군: 오탐 | 0/3 |
| 반복 판정 일관성 | 10/11 |
| 판정 1건 비용 · 지연 | 약 $0.004 · 중앙값 2초 |

**결론.** 연도·날짜 같은 명시적 사실, 의미 반전, 유보 표현 삭제, 눈에 띄는 발언자 교체는 안정적으로 잡고, 원문 사실로 바꿔 쓴 문장은 오탐하지 않는다. 반면 **숫자는 같고 범위만 바뀐 경우**(과기정통부 예산 → 정부 예산)와 **비슷한 인물 여럿 사이의 귀속**(기자 해석 → 팬 반응)은 실제·주입 데이터 모두에서 놓쳤고, 프롬프트 3개 버전과 모델 2개로도 해결되지 않았다. 현재 구조의 한계로 보고 남은 일로 넘겼다.

**범위에서 뺀 것.** 영상 입력 흐름은 대본을 새로 쓰지 않고 구간 선택 + 음성 인식 자막이라 판정 기준과 검증 방법이 달라 제외했다 ([D4](docs/decisions.md)).

## 판정 방식

```
원문 정제 → [규칙] 입력 부족? ──예──> 보류 (입력 문제: "원문을 직접 넣어 주세요")
                  │아니오
                  ├─> [LLM] 게이트: 장르·위험 신호·결함 후보 (대본 인용 + 원문 인용)
                  │      ├─> [코드] 유형 재분류: 원문에만 유보 표현이 있으면 확실성 변화로
                  │      ├─> [코드] 인용 검증: 인용이 실제 대본·원문에 있을 때만 인정
                  │      └─> [코드] 확실성 변화는 건강·금융 위험 신호가 있을 때만 보류
                  ├─> [LLM] 품질 점수 5항목 → 장르별 가중 평균 (참고용)
                  └─> [규칙] 진단: 길이, 말투 혼용, 섹션 반복
```

설계 판단

- **원문은 쇼더스 입력 단계의 "제작에 사용한 원문".** URL을 다시 가져오면 생성기가 본 것과 달라질 수 있다. 포털 하단 안내문·관련 기사·댓글 영역은 정제해서 걷어낸다.
- **입력 부족은 LLM 없이 규칙으로.** 원문 추출이 실패해도 대본이 만들어지고 서비스 확정 검사를 통과한 사례(s04)가 있었다. 대본 탓이 아니라 입력 탓이라는 걸 구분해 알린다.
- **LLM 판단을 코드로 견제.** 근거 인용이 실제로 없으면 보류 사유로 쓰지 않고, LLM이 붙인 유형 이름이 틀려도 유보 표현 규칙으로 바로잡는다. 그래도 "원문에 없다"는 주장 자체가 틀린 경우(s07 요일)는 못 막는다.
- **보류는 게이트만으로.** 품질 점수는 77~96점에 몰려 변별력이 없음을 확인해 참고용으로만 둔다.
- **모델은 gpt-4.1.** gpt-5-mini가 더 정밀하고 쌌지만 판정 1건에 평균 12초, 최대 34초가 걸려 대본을 고치며 반복하는 흐름에 맞지 않았다.

## 대본 하나 바로 판정해 보기

원문과 대본을 텍스트 파일 두 개에 붙여넣으면 바로 결과가 나온다.

```bash
npm run judge:one -- --source examples/source.txt --script examples/script.txt
```

- `source.txt`: 원문. 쇼더스 스튜디오 입력 단계의 "입력한 원고"를 복사하면 판정기가 생성기와 같은 원문을 보게 되어 가장 정확하다.
- `script.txt`: 대본 섹션을 한 줄에 하나씩. `훅: ...`처럼 라벨을 붙여도 되고, 안 붙이면 첫 줄이 훅이 된다.
- `examples/`의 예시는 지어낸 기사와, 결함 하나를 심은 대본이다.
- 옵션: `--title "제목"` · `--score` (품질 점수 추가) · `--json` (결과 JSON 출력) · `--save` (results/에 저장)
- 길이는 글자 수로 추정한다 (쇼더스 1.1배속 기준 초당 약 5.5자, 수집한 섹션들에서 측정).

출력 예시 (예시 입력, 판정 내용은 실행마다 다를 수 있음)

```
판정: ■ 보류
대본 5개 섹션 · 예상 28.8초 (글자 수로 추정)
장르: 보도 · 위험 신호: 건강 X, 금융 X

보류 사유
  · 사실 오류 — 섹션 3 [포인트]
    대본: "120석 모두 개방됩니다"
    원문: "좌석은 기존 120석 가운데 60석만 야간에 개방한다."

진단
  · 예상 길이 28.8초 (서비스 소개 기준 30~45초 밖)
  · 해요체와 합니다체가 섞여 있습니다
```

## 실행

Node.js 20 이상.

```bash
npm install
cp .env.example .env        # OPENAI_API_KEY 입력

npm run judge -- --no-score --repeat 3   # 실제 11건, 게이트만 3회 (약 $0.15)
npm run eval -- results/<파일>.jsonl      # 사람 라벨과 비교 리포트 (.report.md로도 저장)

# 결함 주입 세트
npm run judge -- --data data/injected.jsonl --no-score --repeat 3
npm run eval -- results/<파일>.jsonl --data data/injected.jsonl --labels data/labels_injected.json

npm test                                 # API 없이 정제·규칙·인용 검증·재분류 테스트
```

옵션: `--model <모델>` · `--prompt v1|v2|v2a` (기본 v2a) · `--only s01,s08` · `--no-score` (게이트만)

## 폴더

```
src/            판정기 (judge.ts가 흐름, prompts.ts가 프롬프트 버전, rules.ts·text.ts가 규칙)
src/cli/        일괄 실행(run.ts)·1건 판정(one.ts)·평가(eval.ts)
data/           실제 대본 11건과 사람 판정, 결함 주입 세트와 판정
docs/           기준, 버전별 검증, 결정 기록
results/        모든 실행 결과와 리포트
tools/          쇼더스 스튜디오에서 원문·대본을 내보내는 브라우저 스크립트
examples/       judge:one 예시 입력 (지어낸 기사)
test/           API 없이 도는 테스트
```
